# ADR-002 — Backend em Python usando a biblioteca padrão

- **Status:** Aceita para a versão local simplificada do MVP
- **Data:** 2026-10-22
- **Substitui:** a decisão anterior de utilizar PHP 8.3, Laravel 11, Eloquent, Sanctum/JWT, filas e agendador do Laravel.

## Contexto

A versão original previa uma API REST em Laravel. Para a apresentação em um computador que não pertence à equipe, a instalação do PHP, Composer e respectivas dependências aumenta o risco de problemas de configuração. O objetivo desta adaptação é ter um único processo local, executado diretamente pelo Python, preservando os principais fluxos e regras de negócio que podem ser demonstrados.

## Decisão

Implementar o backend em **Python 3.10 ou superior**, utilizando apenas módulos da biblioteca padrão, principalmente:

- `http.server` (`ThreadingHTTPServer` e `BaseHTTPRequestHandler`) para atender requisições HTTP;
- `json` para receber e responder dados JSON;
- `sqlite3` para persistência;
- `hashlib`, `hmac` e `secrets` para hash de senhas e geração/verificação de tokens locais;
- `urllib.parse`, `mimetypes`, `pathlib` e outros módulos padrão para rotas, arquivos e utilitários.

As rotas da API, as validações, a autorização e as regras de negócio ficam no arquivo `app.py`. Os endpoints atuais estão documentados em `docs/api/api-local.md`.

## Alternativas consideradas

- **Laravel/PHP:** oferece estrutura madura, migrações, autenticação e validação, mas precisa de PHP, Composer e configuração adicional.
- **Flask ou FastAPI:** simplificam a criação de APIs Python, porém exigem instalação e gestão de pacotes externos.
- **Python com biblioteca padrão:** escolhido por reduzir as dependências a uma instalação de Python, suficiente para a escala de demonstração local.

## Consequências

### Positivas

- Não é necessário instalar Composer, Laravel, Flask ou FastAPI.
- O servidor e a API são iniciados com `python app.py` ou por meio do `executar.bat`.
- A lógica de autenticação, validação e regras principais permanece demonstrável e testável.

### Negativas e limites conhecidos

- O código de roteamento e tratamento HTTP é mantido manualmente; não há os recursos e convenções de um framework web.
- Os tokens de sessão ficam em memória e são invalidados quando o processo é encerrado.
- O envio de e-mail usa `smtplib`/`ssl` opcionalmente por variáveis de ambiente; sem SMTP, o link de verificação é exibido para uso local. Não há fila assíncrona nem agendador de jobs dedicado.
- A implementação é voltada para execução local e **não deve ser exposta diretamente à internet nem tratada como pronta para produção**.
- A validação e os testes precisam acompanhar qualquer alteração nas rotas e regras de negócio.

## Escopo

Esta decisão descreve a implementação local simplificada, não a arquitetura de produção inicialmente planejada. Uma futura versão implantada institucionalmente deve reavaliar o uso de um framework web e os controles operacionais e de segurança necessários.
